# 統合開発・ドキュメント進行スキル

- **バージョン**: v2.1.0
- **ステータス**: done

`/ai-docs <概要または指示>`。引数なしは現在の進捗から次工程を判定する。

## 前提

リポジトリルートの `AGENTS.md` と [運用インデックス](../../../docs/operations/OPERATIONS.md)、そこから参照される全運用文書を読む。上位を正とし、Layer 0（運用） > Layer 1（REQ） > Layer 2（設計SPEC） > Layer 3（検証VERIFY）に従う。旧詳細設計はSPECへ統合済み。

## 診断とアクション

まず下記の集約手順で対象機能を特定し、各インデックスと全機能文書の存在・ステータスを上位から確認して最初の未完了工程を進める。表内の文書パスは既存文書の更新を優先し、登録は既存行の更新を含む。

| 状態 | アクション |
| :--- | :--- |
| REQ未完了 | 背景、目的、スコープ、ユースケース、受け入れ基準を `docs/req/features/<機能名>.md` に具体化し、`docs/req/REQ.md` に登録 |
| REQ全件done、SPEC未完了 | 振る舞い、入出力、業務ルール、異常系、アーキテクチャ、データモデル、状態管理、API、コンポーネント構成、永続化、設計理由を `docs/spec/features/<機能名>.md` にまとめ、`docs/spec/SPEC.md` に登録。UIがあれば `docs/spec/screens.drawio` も同期 |
| SPECまで全件done、検証計画未完了 | `docs/verification/features/<機能名>.md` にREQ/SPECとケースの対応、前提・環境、入力、手順、期待結果、合否基準、検証方法を記載し、`docs/verification/VERIFY.md` に登録 |
| REQ・SPEC・検証計画とインデックス全件done | Layer 2に従い実装・テストを行い、確定計画で検証。結果・証跡を `docs/verification/results/<機能名>.md` に記録してVERIFYインデックスを更新 |
| 結果が未完了 | 失敗・未実施を解消して再検証し、対象コミット、日時、環境、実測結果、判定、証跡を同期 |

## ゲートと変更管理

文書はバージョンと `draft` を付ける。変更時は対象文書とインデックスも `draft` に戻す。編集段階ではコミットせず、文書作成・更新後は下記のレビュー手順を実行する。`wip` はowner承認が必要で、次工程へは進めない。

実装前には検証結果を要求しない。計画のdoneは検証済みを意味しない。結果登録によるインデックスdraft化の後も、確定計画に基づく検証・不具合修正・再検証は継続できる。上位・計画変更時は影響範囲を停止し上位から再確定する。必須ケース合格と結果文書・インデックスのレビュー完了で実装完了とする。

運用体系そのものの変更依頼はLayer 0の編集として扱い、関連文書・スキルを同期した後、レビュー手順まで実行する。製品機能の後続工程へ進む操作と区別する。

## 作成・更新後のレビュー（必須）

1. 今回作成・更新した文書と対応インデックスを対象に、以下の「レビュー基準と判定」に従って同じ呼び出し内でレビューする。別スキルの呼び出しやユーザーによる追加指示を必要としない。
2. 上位・同位文書、必須項目、移行ゲートを確認する。具体化できる指摘は依頼範囲内で修正し、修正箇所と影響範囲を再レビューする。ownerの判断が必要な要件は推測して確定しない。
3. PASSなら内蔵の判定手順に従い対象文書とインデックスを `done` に更新し、今回の変更のみをコミットする。ユーザーがコミット禁止などを指定している場合はその指示を優先する。
4. 未完了だが矛盾がなければ、`wip` での中間コミットについてownerの承認を得る。承認がなければ `draft` を維持しコミットしない。FAILなら未解消の矛盾と必要な判断を報告し、`done`・`wip` にせずコミットしない。
5. レビュー判定、ステータス、コミット有無、未解決事項を報告する。レビュー完了を理由に、依頼範囲外の次レイヤーや実装へ自動的に進まない。

## 横断ADRの作成・更新

`/ai-docs ADR <判断の概要>` または要求・設計・検証を横断する意思決定の記録依頼では、通常の未完了工程診断より先に [ADR運用](../../../docs/operations/ADR.md) を読み、`docs/adr/NNNN-<topic>.md` を [テンプレート](../../../docs/adr/TEMPLATE.md) から作成する。[ADR一覧](../../../docs/adr/ADR.md) へ登録し、関連REQ/SPEC/VERIFYと相互参照する。

ADRはどの工程でも起案できるが上位のdoneゲートを迂回しない。背景・比較案・理由・各レイヤーへの影響と反映状況・決定者・未決事項を記録する。文書ステータスと決定状態を区別し、未確定の上位やowner判断が残る場合は採用を確定しない。採用判断の変更は後継ADRを作り履歴を残す。作成・更新後は本スキルの必須レビューを実行する。

## レビュー基準と判定

### 参照と検査

`AGENTS.md`、[OPERATIONS.md](../../../docs/operations/OPERATIONS.md)と全運用文書を読み、対象を次のように分類する。

| 対象 | 準拠基準・同位文書 |
| :--- | :--- |
| Layer 0: AGENTS、運用、スキル | ownerの変更指示と他の全Layer 0文書。新体系に対する下位文書とスキルの参照・ゲート整合性も確認 |
| Layer 1: `docs/req/` | Layer 0、REQインデックス、他の要件 |
| Layer 2: `docs/spec/` | Layer 0、対応REQ、REQインデックス、SPECインデックス、他の設計、画面仕様 |
| Layer 3: `docs/verification/` | Layer 0、対応REQ/SPEC、各インデックス、他の計画・結果。結果は確定計画と証跡にも照合 |

設計は現行のSPECで確認する。削除済みのレガシー資料・互換案内を再作成しない。目的・スコープ・受け入れ基準の勝手な変更、命名・データ構造・画面の不整合、必須項目の不足、保留事項を検査する。

検証計画はREQ/SPECとのケース対応、正常・異常・境界値、要求された非機能項目、前提、手順、期待結果、測定可能な合否基準を確認する。結果は対象コミット・環境・日時・ケース別実測結果・判定・証跡を確認する。計画のdoneと検証済みを区別し、必須ケースに失敗・未実施や未解決の完了阻害事項があれば結果をPASSにしない。実装前には結果文書を要求しない。

### 判定

- **PASS**: 必須項目が完了し上位・同位と整合していれば、対象文書とインデックス内の対象行をdoneに更新する。インデックス自身は全体の必須項目・全対象文書が完了した場合のみdoneにする。レビュー対象の変更だけをコミットし、結果と通過したゲートを報告する。
- **未完了だが矛盾なし**: ownerにwipで中間コミットしてよいかを問い、承認時だけ文書・対応行をwipにしてコミットする。後続ゲートは通過しない。
- **FAIL**: done・wipへ変更せずコミットしない。対象箇所、比較した上位・同位文書、矛盾内容、修正案を報告する。

文書内容を修正した時は対象文書とインデックスをdraftへ戻す。上位の変更が必要なら上位を先に修正・確定する。doneはレビュー完了、developマージは正式確定として区別する。

### ADRのレビュー

`docs/adr/` は独立レイヤーではなく横断する判断記録として扱い、[ADR運用](../../../docs/operations/ADR.md)、ADR一覧、関連REQ/SPEC/VERIFYと他の関連ADRを読む。背景・比較案・決定理由・決定者・影響・反映状況・相互参照・後継関係を確認する。正本を上書きせず上位優先とゲートを守っているか、文書ステータスと決定状態を混同していないかを確認する。

採用ADRは必要な正本への反映と整合性が完了するまでPASSにしない。未決提案はWIP判定、不採用は理由が完備すれば文書完了として扱える。テンプレートは構成をレビューし、未記入欄を実際の判断の未決事項と混同しない。PASS/WIP/FAILの処理は共通判定に従い、一覧の対応行も同期する。

## 既存機能への集約（追加・更新前に必須）

[運用ルール](../../../docs/operations/OPERATIONS.md) の「機能単位の集約と重複防止」に従う。

1. REQ/SPEC/VERIFYの一覧と関連文書を検索し、目的・責務・データ・ユースケース・受け入れ基準を比較する。機能名の文字列一致だけで判断しない。
2. 既存機能の拡張・派生・例外・追加ケースなら、その機能の文書・既存一覧行へ集約する。共通定義は正本を参照し、追加依頼ごとに類似機能を新設しない。
3. 独立した責務・スコープを持つ場合のみ新設し、近い既存機能との差と分割理由を記録する。無関係な責務まで統合しない。
4. 3レイヤーで同じ機能単位と項目間の対応を維持する。統合時は旧IDとの対応、リンク、ADR参照を同期し、受け入れ基準・ケース・過去の結果と証跡を失わない。内容変更は上位確定後に下位へ同期する。
5. 内蔵レビューで集約先、新設・分割理由、類似項目の重複、一覧と3レイヤーの対応、参照・ID・履歴の維持を確認する。報告には既存機能へ集約したか新設したかと、その理由を含める。
