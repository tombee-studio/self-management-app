# ADR-0002: 全9機能へDDDと契約駆動設計を適用する

- **バージョン**: v1.1.0
- **ステータス**: done
- **決定状態**: superseded
- **日付**: 2026-11-01（JST）
- **決定者**: owner（本セッションで設計方式を明示）、具体化・整合レビューはai-docs

## 背景・課題・制約

機能別設計は画面・DB・サービスの処理順が中心で、業務の整合性境界と公開契約が暗黙だった。途中の実装にもUIからDBを直接更新する構造が残り、型・失敗・再試行・競合条件をadapter間で検証しにくい。ownerから各機能をドメイン駆動設計と契約駆動設計の組み合わせで作り直す指示を受けた。

既存の9機能・60 AC・画面の業務条件・旧項目IDは維持する。今回の対象は要求への設計制約追加、設計・機械可読契約・検証計画の再確定。途中の実装コードは保持し、今回の設計に適合済みとしてコミットしない。

## 選択肢と比較

| 選択肢 | 利点 | 欠点・制約 | 採否理由 |
| :--- | :--- | :--- | :--- |
| 従来の画面/DB中心設計を継続 | 既存実装の修正が少ない | 業務境界・公開保証が暗黙のまま | ownerの指示と合わない |
| DDDだけを適用 | 所有・不変条件を整理できる | API/Port/イベントの形式・失敗保証を統一できない | 単独では不十分 |
| 契約だけを定義 | consumer/providerの接続を検証できる | DBやDTOを業務モデルと混同する問題が残る | 単独では不十分 |
| DDD＋契約駆動 | 集約の不変条件と境界の保証を一貫して検証できる | adapter・版メタデータ・テストの追加が必要 | ownerの指定方針として採用 |

## 決定と理由

ExpenseLedger、CategoryCatalog、Budgetingの業務モデルを中心に、外部決済をACL、同期をReplicationの支援モデルとして整理する。日次・履歴はLedgerのReadModel、共通UI・アイコンは技術的能力とし、すべての機能に業務集約を無理に置かない。

Domainは値型・集約・不変条件・所有するPort、ApplicationはユースケースとUnitOfWork、Infrastructureはdrift/HTTP/通知SDK等のadapter、Presentationは状態と表示を担当する。公開契約には型、事前条件、事後条件、失敗時保証、冪等性・版を定める。HTTP/EventはOpenAPI/JSON Schema、内部Portは型付き契約表と共通providerテストを正本とする。

集約版、Outbox送信revision、LWW更新時刻を分離するためDB目標を版3へ改訂する。版1/2からの移行を計画し、途中実装の版2DBを初期化しない。wire版2は維持し、厳密な公開形へprovider adapterを先行対応する。

## リスク・トレードオフ

抽象型や契約が増えるため、ReadModel・技術的能力を業務集約に仕立てず、既存機能内へ集約する。複数コンテキストにまたがるカテゴリ廃止は既存REQの即時整合を守るため、同じローカルUnitOfWorkで調整する。外部同期の部分成功をローカルCommandの原子性と混同しない。

JSON Schemaはgrapheme・集約版・カテゴリ存在などの意味を保証できないので、Domain/Port契約テストを併用する。既存の単体テスト結果・途中の実装は新契約の合格として流用しない。
