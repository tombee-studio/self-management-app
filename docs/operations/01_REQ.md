# 01_REQ.md - Layer 1: 要求 / 要件定義（REQ）プロセス運用ルール

- **バージョン**: v2.0.0
- **ステータス**: done

本ドキュメントは、開発プロセスの第1階層である**Layer 1: 要求 / 要件定義（REQ: Requirements）**における運用ルールおよび関連ドキュメントを規定します。

---

## 1. プロセス概要と目的

- **フェーズ**: Layer 1: 要求 / 要件定義（REQ）
- **目的**: **Why / What の明確化**
  - 何を作るのか、なぜ作るのか、誰のための課題解決かを定義する。
  - プロダクトや機能の背景、目的、スコープ、受け入れ基準を明確にし、開発の方向性を確定させる。
- **階層位置**: 第1階層（$$\text{Layer 0 (運用プロセス)} \succ \text{Layer 1 (要求: REQ)} \succ \text{Layer 2 (設計: SPEC)} \succ \text{Layer 3 (検証: VERIFY)}$$）
  - Layer 0（運用プロセス定義）のメタ規範に従う。
  - 後続のすべての工程（Layer 2: SPEC, Layer 3: VERIFY）は、本要件定義の目的に従わなければならない。


---

## 2. 関連ドキュメント・成果物

| ドキュメント / 成果物 | 役割・内容 | 管理場所 |
| :--- | :--- | :--- |
| **要件定義書インデックス** | プロダクト全体の背景、目的、ターゲット層、機能要件一覧 | [docs/req/REQ.md](../req/REQ.md) |
| **機能別要件定義書** | 各機能のユーザーストーリー、ユースケース、受け入れ基準 | `docs/req/features/<機能名>.md` |
| **受け入れ基準 (Acceptance Criteria)** | その機能が完成したとみなすための検証可能な達成条件 | 各機能の完了要件 |

---

## 3. 運用手順・作業フロー

1. **背景と課題のヒアリング・整理**:
   - 解決したい課題、期待される効果、スコープ（対象内外）を明確にする。
2. **ユースケース・受け入れ基準の策定**:
   - ユーザー視点での操作シナリオと、機能が満たすべき受け入れ基準を具体化する。
3. **ドキュメントの作成 (`/ai-docs`)**:
   - 統合スキル [.agents/skills/ai-docs/SKILL.md](../../.agents/skills/ai-docs/SKILL.md) を活用し、機能別要件定義書（`docs/req/features/<機能名>.md`）を作成する。
   - [docs/req/REQ.md](../req/REQ.md) の「2. 要件定義一覧 (Requirements)」テーブルに機能名、リンク、概要、ステータス（`draft`）を追記する。
   - ドキュメントヘッダーにバージョン（例: `v0.1.0`）とステータス `draft` を付与する。
4. **レビューと確定 (`/ai-docs` のレビュー工程)**:
   - `/ai-docs` は作成後に[ai-docsスキル](../../.agents/skills/ai-docs/SKILL.md) 内のレビュー工程を実行し、プロダクト全体の目的（`REQ.md`）や他の機能要件との整合性を検証する。
   - **矛盾なし（PASS）**: ドキュメントおよびインデックスのステータスが `done` に更新されコミットされる。
   - **作業途中（WIP）**: 未完了項目がある下書きの場合、ownerに `wip` に更新してコミットするかを問い、承認されればステータス `wip` でコミットされる。
   - **矛盾あり（FAIL）**: コミットは行われずステータスも変更されない。出力されたコメントの指摘事項をもとに修正する。

---

## 4. プロセス移行ゲート（完了条件）

次工程である**Layer 2: 設計（SPEC）**へ進むためには、以下の条件をすべて満たす必要があります。

- [ ] 対象機能の要件に関するすべてのドキュメント（`docs/req/features/*.md`）および [docs/req/REQ.md](../req/REQ.md) のステータスが **`done`** になっていること。
- [ ] 目的、スコープ、受け入れ基準に未合意・曖昧な点が残っていないこと。
- [ ] ※ 1つでも `draft`, `wip`, または `review` のドキュメントがある場合は、Layer 2（SPEC）フェーズへ進んではならない。


## 5. 追加要求の集約

[機能単位の集約ルール](OPERATIONS.md)に従い、既存要求の目的・スコープ・ユースケースと比較し、拡張や派生は既存機能の要求文書へ反映する。インデックスも既存行を更新し、新規機能に分ける場合は責務の境界と分割理由を記録する。
