# 03_VERIFY.md - Layer 3: 検証（VERIFY）プロセス運用ルール

- **バージョン**: v2.0.0
- **ステータス**: done

## 1. 目的と位置づけ

Layer 1（REQ）の受け入れ基準と Layer 2（SPEC）の設計を満たすことを確認するため、検証計画、検証ケース、実施結果、証跡を Layer 3（VERIFY）に集約する。検証の都合で要件・仕様・設計を変更せず、必要な変更は上位文書を先に修正・確定して反映する。

## 2. 成果物

| 成果物 | 内容 | 管理場所 |
| :--- | :--- | :--- |
| 検証インデックス | 共通検証方針、対象環境、機能別計画・結果へのリンクとステータス | [VERIFY.md](../verification/VERIFY.md) |
| 機能別検証計画・ケース | 対応REQ/SPEC、検証範囲・対象外と理由、検証方法、前提、入力、手順、期待結果、合否基準 | `docs/verification/features/<機能名>.md` |
| 検証結果・証跡 | 実施対象のコミット、日時、環境、ケース別実測値・判定、ログ等への参照、不具合・再検証結果 | `docs/verification/results/<機能名>.md` |

## 3. 実装前の計画確定

1. REQ・SPECの各インデックスと各レイヤーの全ドキュメントが `done` であることを確認する。
2. `/ai-docs` で検証計画を `draft` として作成する。受け入れ基準・仕様項目に識別子を付け、各検証ケースとの対応を示す。
3. 正常系、異常系、境界値、状態遷移、および上位文書で要求される性能・セキュリティ等の非機能項目を扱う。単体・結合・E2E・手動確認の適切な方法と実行コマンドを定める。対象外は理由を記録する。
4. 前提データ、環境、手順、期待結果と測定可能な合否基準を記載し、インデックスに登録する。
5. `/ai-docs` 内のレビュー工程で上位・同位文書との整合性と網羅性を確認する。計画とインデックスがすべて `done` になったら実装へ進める。

## 4. 実装後の検証と結果記録

1. 確定済み計画に従って検証を実施し、結果文書を `draft` として作成・登録する。未実施を合格として扱わない。
2. ケースID、対象コミット、実施日時・環境、期待結果と実際の結果、PASS/FAIL/未実施、証跡への参照を記録する。失敗・未実施には理由、不具合への参照、対応状況を記載する。
3. 実装不具合は修正・再検証する。上位文書の変更が必要なら上位同期後、影響する計画を `draft` に戻し再レビューしてから対応する。
4. `/ai-docs` 内のレビュー工程で結果の完全性、証跡、受け入れ基準充足を確認する。必須ケースの未実施・失敗や未解決の完了阻害事項がある場合は完了扱いにしない。

## 5. ゲートとステータス

- **実装開始**: REQ・SPEC・VERIFYの計画とインデックスがすべて `done`。実装前には結果文書を要求しない。
- **実装完了**: 上記に加え、全必須検証に合格し、結果文書とインデックスが `/ai-docs` のレビュー工程を経て `done` であること。
- 計画の `done` は計画の確定を意味し、検証実施済みを意味しない。結果登録・更新時は結果文書とインデックスを `draft` に戻す。計画の内容が変わらなければ計画の `done` は維持する。
- 結果記録によるインデックスの `draft` 化は、確定済み計画に基づく検証・不具合修正・再検証を妨げない。計画・上位文書が変更された場合は再確定まで影響範囲の実装を停止する。

## 6. 検証の集約

[機能単位の集約ルール](OPERATIONS.md)に従い、追加検証は対応REQ/SPECと同じ機能の計画・ケースへ組み込み、既存ケースと重複させない。結果は同じ機能の結果文書へ実施単位で記録し、過去の対象コミット・環境・判定・証跡を保持する。ケースを統合する場合も旧IDとの対応を残す。
