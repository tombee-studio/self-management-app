# 02_SPEC.md - Layer 2: 設計（SPEC）プロセス運用ルール

- **バージョン**: v2.0.0
- **ステータス**: done

## 1. 目的と範囲

Layer 1（REQ）の目的・受け入れ基準に従い、振る舞い（What）と実現方式（How）を同じ Layer 2（SPEC）で定義する。仕様（基本設計）と詳細設計をまとめて「設計」と呼び、本レイヤーで管理する。

## 2. 成果物

| 成果物 | 内容 | 管理場所 |
| :--- | :--- | :--- |
| 設計インデックス | 共通仕様、全体アーキテクチャ、共通基盤、技術スタックと選定理由 | [SPEC.md](../spec/SPEC.md) |
| 機能別設計書 | 対応REQ、ユーザーフロー、入出力、バリデーション、業務ロジック、エラー、データモデル、コンポーネント構成、状態管理、永続化、API・インターフェース | `docs/spec/features/<機能名>.md` |
| 画面仕様 | ワイヤーフレームとコンポーネント仕様一覧を同一キャンバスに記載 | `docs/spec/screens.drawio` |

## 3. 作業フロー

1. REQインデックスと当該レイヤーの全ドキュメントが `done` であることを確認する。
2. `/ai-docs` で機能別設計書を `draft` として作成・更新し、対応要件と設計判断の理由・トレードオフを記録する。
3. UIがある場合は `screens.drawio` の該当タブを更新する。インデックスに機能名、文書リンク、対応REQ、概要、ステータスを登録し、インデックスも `draft` にする。
4. 要件の変更が必要ならREQを先に修正・確定させる。
5. `/ai-docs` 内のレビュー工程で上位REQ・運用ルールおよび同位の共通仕様・設計・画面仕様との整合性を確認する。判定・コミットは [OPERATIONS.md](OPERATIONS.md) に従う。

## 4. Layer 3への移行ゲート

- SPECインデックスと当該レイヤーの全ドキュメントが `done` であること。
- 振る舞いと実現方式が具体的で、実装者が判断を補わずに実装できること。
- UIがある場合、画面仕様が完成・合意されていること。
- `draft`・`wip`・`review` が残る場合は検証計画の策定へ進まない。

## 5. 設計の集約

[機能単位の集約ルール](OPERATIONS.md)に従い、対応REQの機能単位を継承して既存設計へ追記・更新する。共通設計を複製せず正本を参照する。分割が必要なら親機能、責務の境界、分割理由を明示し、類似機能を独立した一覧行として乱立させない。
