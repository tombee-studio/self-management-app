# IMPL.md - 実装（Implementation）プロセス運用ルール

- **バージョン**: v2.0.0
- **ステータス**: done

本ドキュメントは、ドキュメント策定工程（Layer 1: REQ 〜 Layer 3: VERIFYの検証計画）の完了後に実施する**実装（Implementation）プロセス**における運用ルールおよびコーディング規約・品質基準を規定します。

> [!NOTE]
> 実装（ソースコード・テスト）はプロダクト成果物そのものであり、ドキュメント体系（Layer 0 〜 Layer 3）には含まれませんが、開発パイプラインにおいて設計を具現化する極めて重要なプロセスです。

---

## 1. プロセス概要と基本原則

- **フェーズ**: 実装（Implementation）プロセス
- **目的**: **高品質なコード作成とテストの担保**
  - 設計（Layer 2: SPEC）に基づき、堅牢で保守性の高いコードとテストを実装する。
- **基本原則: 常に設計と矛盾がないこと（Design-First）**:
  - 実装は、必ず上位の設計（Layer 2: SPEC）、および運用プロセス（Layer 0）に従わなければならない。
  - **実装が設計と矛盾することは厳禁**とする。
  - **上位同期ファースト（下位独断変更の禁止）**: 実装中に設計の矛盾・考慮漏れ・技術的制約による実現困難な点が発生した場合は、コード側で勝手に辻褄を合わせず、必ず上位ドキュメント（Layer 2: SPEC / Layer 1: REQ）を先に修正・確定させてからコードへ同期する。

---

## 2. 成果物・コード管理

| 成果物 / コード | 役割・内容 | 管理場所 |
| :--- | :--- | :--- |
| **ソースコード** | 設計書に沿ったビジネスロジック、データモデル、UI/API実装 | プロジェクトのソースコードディレクトリ |
| **ユニットテストコード** | コアロジックの正常系・異常系・境界値を網羅する自動テスト | テストコードディレクトリ |
| **静的解析・型定義** | Lint、型チェック、フォーマッタの合格 | プロジェクトルートの設定ファイル |

---

## 3. コーディング＆設計原則

1. **設計への忠実性**: 設計書で定義されたデータモデル、インターフェース、コンポーネント構成に正確に従って実装する。
2. **責務の明確化とモジュール性**: 責務を適切に分離し、保守性・可読性の高いコードを作成すること。
3. **テストの重視**: コアロジック（ビジネスロジック、バリデーション、データ変換・計算処理など）には単体テストを作成・維持し、リグレッションを防ぐこと。
4. **ユーザー体験（UI/UX）**: 直感的で使いやすく、洗練されたモダンなデザインと適切なフィードバック・エラーハンドリングを提供すること。
5. **安全でクリーンな変更**: 不要なコードやデバッグログを残さず、静的解析・型チェック・フォーマットをパスさせること。
6. **セキュリティ＆プライバシー重視**: センシティブ情報や機密データの取り扱いに留意し、不要な外部送信や不適切なログ出力を避けること。安全なデータ永続化とアクセス制御・バリデーションを徹底する。

---

## 4. 運用手順・作業フロー

1. **前提ドキュメントの完了ゲート確認**:
   - 対象機能に関わる要件（Layer 1: REQ）、設計（Layer 2: SPEC）、検証計画（Layer 3: VERIFY）のすべてのドキュメントが **`done`** になっていることを確認する。いずれかが `draft`, `wip`, または `review` の場合は実装に着手してはならない。
2. **統合開発スキルの活用 (`/ai-docs`)**:
   - 統合スキル [.agents/skills/ai-docs/SKILL.md](../../.agents/skills/ai-docs/SKILL.md) の標準手順に沿って実装を進める。
3. **コアロジック・データモデルの実装と単体テスト**:
   - ビジネスロジックを分離実装し、単体テストを作成して境界値・例外系まで網羅する。
4. **インターフェース層の実装**:
   - UIコンポーネント、APIエンドポイント、またはCLIコマンド等を実装する。
5. **ドキュメント整合性・同期の検証**:
   - 実装と設計（Layer 2: SPEC）との間に乖離や矛盾がないかを検証する。

---

## 5. 品質保証＆セルフレビューチェックリスト

実装完了後は以下をセルフチェックすること:
1. [ ] **設計（Layer 2: SPEC）と完全に整合しており、矛盾がないこと**
2. [ ] 静的解析（Lint、型チェック）を実行し、エラー・警告がゼロであること
3. [ ] コアロジックの単体テストがすべてパスしていること
4. [ ] 目的外の不要なコードやコメントアウト、デバッグログが残っていないこと
5. [ ] 例外処理・エラーハンドリングが適切に実装されていること

## 6. 検証計画と結果の同期

実装開始時にはREQ・SPECおよびVERIFY計画と各インデックスの全件 `done` を確認する。検証結果は実装後に作成するため開始条件には含めない。

確定済みの検証計画に従ってテストと静的解析を実施し、対象コミット、環境、ケース別の実際の結果・判定、証跡を `docs/verification/results/<機能名>.md` に記録し、VERIFYインデックスを更新する。結果文書とインデックスは `draft` とし、失敗の修正・再検証後に内蔵のレビュー工程を実行する。全必須ケースの合格と結果文書・インデックスの `done` をもって実装完了とする。詳しい運用は [03_VERIFY.md](03_VERIFY.md) に従う。
