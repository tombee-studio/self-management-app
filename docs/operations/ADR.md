# ADR - 横断する意思決定記録の運用

- **バージョン**: v0.1.0
- **ステータス**: done

## 1. 位置づけ

ADR（Architecture Decision Record）は要求・設計・検証にまたがる判断の背景、選択肢、決定、影響を記録する。独立したレイヤーやREQ/SPEC/VERIFYより優先する規範にはしない。仕様・受け入れ基準・検証ケースの正本は各レイヤーに置き、ADRから参照する。

## 2. 作成と管理

`/ai-docs ADR <判断の概要>` で [テンプレート](../adr/TEMPLATE.md) をコピーし、`docs/adr/NNNN-<topic>.md` を作成する。NNNNは既存の最大番号に1を足した4桁連番（初回0001）、topicは英小文字・数字・ハイフンで表す。既存番号を再利用しない。

[ADRインデックス](../adr/ADR.md)にID、題名、対象レイヤー、文書リンク、文書ステータス、決定状態を登録する。新規・変更時は本文とインデックスを `draft` にする。

ADRの相談・草案はどの工程でも作成できる。上位が未確定でも選択肢の検討を記録できるが、ADRによって後続工程のdoneゲートを迂回しない。未確定の上位文書を明示し、関連する判断の採用はその確定まで保留する。

## 3. 必須項目と状態

- ID、題名、バージョン、文書ステータス、日付、決定者。
- 背景・課題・制約、比較した選択肢と利点・欠点。
- 決定と理由、要求・設計・検証それぞれへの影響、リスクとトレードオフ。
- 関連REQ/SPEC/VERIFYの文書・項目IDへの参照と反映状況。影響なし・未作成なら理由を明記し、存在しない文書へリンクしない。
- 未解決事項、旧ADR・後継ADRとの関係。

文書ステータスは共通の `draft / wip / review / done`。別項目の決定状態は `proposed`（提案）、`accepted`（採用）、`rejected`（不採用）、`superseded`（後継で置換）とする。文書のdoneだけで判断の採用を意味しない。決定者と判断根拠を記録し、ownerの判断が必要な選択は独断でacceptedにしない。

## 4. 同期・レビュー・変更履歴

上位変更が必要ならREQ→SPEC→VERIFYの順に修正・確定し、関連文書からADRへ逆リンクも付ける。採用ADRのdoneには必要な正本への反映・整合性確認を要求する。未完了の反映を残した採用案はdraftのままとする。提案中で採用判断が未完了ならWIP判定の対象とする。不採用は理由の記録により文書を完了できる。

`ai-docs` は作成・更新後に内蔵のレビュー工程を実行する。背景、選択肢、決定理由、関連レイヤーとの整合性、反映状況、状態と決定者を検査し、PASSなら本文とインデックスをdoneにしてコミットする。WIPはowner承認、FAILはコミットしない。

既存の採用判断を変更する場合は新しいADRを起こし、旧ADRの決定内容を消さず、後継リンクとsupersededを記録する。旧ADRの変更もdraft化・再レビューする。

ADRは独立した一括ゲートを追加しない。対象工程に影響する未決事項・未反映事項はその工程の正本にも明記し、解消するまで当該工程の完了を認めない。無関係なADRや文書テンプレートは工程の完了を妨げない。
